# Decision Log

Each entry answers three questions: **what** was chosen, **why**, and **what was rejected**. Entries are never deleted. When a decision changes, add a new entry that replaces the old one (write "supersedes D-xx").

Format: `D-xx — title` · status · date

---

### D-01 — The agent opens the connection (reverse connection) · accepted · 2026-11-19
- **What:** the agent dials out to the server over WSS and keeps the connection open.
- **Why:** hosts sit behind NAT, so the server cannot reach them. Outbound connections are almost always allowed by firewalls. Over port 443 with WebSocket, the connection looks like normal web traffic.
- **Rejected:** a mesh VPN (Tailscale/WireGuard), because it needs another component and doesn't serve the learning goal as well. Opening ports on the router, because it isn't always possible and isn't safe.

### D-02 — One control WS per agent + one new WS per session · accepted · 2026-11-19
- **What:** the control connection carries only small JSON messages. Every shell, file view or tunnel opens a new WebSocket, and the server joins the two WebSockets together.
- **Why:** the server's relay is just "copy bytes both ways" (`io.Copy`). No home-made framing or flow-control protocol. A stuck session doesn't affect other sessions. Easy to debug, because one session is one connection. MeshCentral uses the same approach.
- **Rejected:** multiplexing over one connection (yamux/smux). It saves connections but adds concepts (stream IDs, windows, backpressure) and a dependency we don't need yet.
- **Consequence:** every session costs one extra TLS handshake, a few hundred milliseconds. That is acceptable.

### D-03 — Uploads/bulk sends: the server stores the file, agents download it · accepted · 2026-11-19
- **What:** a file is uploaded to the server once. The server then sends a `fetch` message to each agent, and each agent downloads it over HTTP.
- **Why:** sending to 1 host and to 50 hosts uses the same code. HTTP downloads can be retried on failure. The server doesn't have to fan one stream out to many connections.
- **Rejected:** streaming the upload from the browser straight into agent sessions. That is complicated for many targets and fails entirely when one agent is slow.
- **Consequence:** transfer status lives in memory. If the server restarts mid-transfer, the status is lost, but the final results are still in the audit log.

### D-04 — HTTP server uses stdlib `net/http`, no framework · accepted · 2026-11-19
- **Why:** Go 1.22+ supports `mux.HandleFunc("GET /api/hosts/{id}", …)`. Learning `net/http` means learning the foundation every framework is built on.
- **Rejected:** Gin, Echo, Fiber, Chi.

### D-05 — SQLite (`modernc.org/sqlite`) + hand-written SQL · accepted · 2026-11-19
- **Why:** one database file, no separate DB server. A pure-Go driver (no CGO) keeps cross-compiling easy. Writing SQL by hand makes it obvious what happens.
- **Rejected:** ORMs (GORM, ent), Postgres/MySQL (not needed yet), `mattn/go-sqlite3` (needs CGO).
- **Migrations:** at first, a single `schema.sql` with `CREATE TABLE IF NOT EXISTS`. Versioned migrations are added the first time a schema change would break existing data.

### D-06 — Frontend: HTML + vanilla JS + CSS, embedded, no build step · accepted · 2026-11-19
- **Why:** only one toolchain (Go). Web files are served from `embed.FS`, so the server stays a single binary. The MVP has few, simple pages.
- **Rejected:** React/Vue/Svelte + Vite (a second toolchain with many new concepts), Tailwind (needs a build step unless you use the play CDN), htmx (worth reconsidering if hand-written JS starts repeating).
- **Allowed third-party library:** xterm.js (+ fit addon), vendored into `web/vendor/` with a pinned version, not loaded from a CDN, so the dashboard works without internet access.

### D-07 — TLS is handled by Caddy, not by the headnode server · accepted · 2026-11-19
- **Why:** Caddy handles Let's Encrypt automatically with about 3 lines of config. The server code needs to know nothing about certificates. In development, the server simply runs plain HTTP.
- **Rejected:** `autocert` inside Go (more code and state in the server), nginx (longer config).

### D-08 — WebSocket library: `github.com/coder/websocket` · accepted · 2026-11-19
- **Why:** small API, `context` support for timeouts and cancellation, and `websocket.NetConn`, which lets a tunnel session be treated like a `net.Conn`.
- **Rejected:** `gorilla/websocket` (also good, but lower-level, and you must handle concurrent writes yourself).

### D-09 — Agent secret: random 256-bit token, stored as SHA-256 · accepted · 2026-11-19
- **Why:** the secret is machine-generated with high entropy, so a fast hash is already safe. Bcrypt is only needed for guessable human passwords. Comparison uses `subtle.ConstantTimeCompare`.
- **Also applies to:** enroll tokens and login session tokens (cookies). User passwords still use bcrypt.

### D-10 — No architecture prepared for features that haven't been chosen · accepted · 2026-11-19
- **What:** remote desktop, CCTV, plugins, multiple servers, auto-update and 2FA get no "hooks" or abstractions now.
- **Why:** YAGNI. Guesses about future needs are usually wrong, and a wrong abstraction costs more than a refactor later.

### D-11 — Linux system info is read directly from `/proc` · accepted · 2026-11-19
- **Why:** the learning goal (seeing exactly where CPU% and RAM numbers come from), and no dependency. We only need `/proc/stat`, `/proc/meminfo`, `/proc/uptime`, `/etc/os-release` and `syscall.Statfs`.
- **Rejected (for now):** `gopsutil`. **Revisit** when the Windows agent is built, because reading system info on Windows through syscalls is much more work.

### D-12 — Linux agent first, Windows later · accepted · 2026-11-19
- **Why:** a PTY on Linux is simple (`creack/pty`), while Windows needs ConPTY and a different service manager. Prove the foundation (connections, relay, files) on one OS first.
- **Consequence:** OS-specific code is split per file with build tags (`shell_linux.go`, `shell_windows.go`), but only once a Windows file is actually written.

### D-13 — Name: `headnode`; binaries `headnode`, `headnode-agent`, `hnctl` · accepted · 2026-11-19
- **What:** Go module `headnode`. The server binary is just `headnode`, the agent is `headnode-agent`, the CLI client is `hnctl`. The login cookie is `hn_session`.
- **Why:** the server is the "head" that all hosts connect to. The agent name says what it belongs to. `hnctl` follows the common `*ctl` convention (`kubectl`, `systemctl`) and is short to type.

### D-14 — Language: English everywhere · accepted · 2026-11-19
- **What:** code, identifiers, comments, docs and commit messages are all in English.
- **Why:** technical detail is easier to follow in English, and it matches the stdlib, libraries and most reference material.

### D-15 — UI style modeled on the Tailscale admin console, light + dark · accepted · 2026-11-20
- **What:** warm-gray palette, left sidebar (org name on top, user at the bottom), tables without card boxes, one muted blue accent. Both light and dark themes, switched by `prefers-color-scheme`. Details in [design.md](design.md).
- **Why:** the owner prefers this look. It is quiet and readable for long admin sessions. Because every color is a CSS variable, the dark theme is just one extra block of values, not a second stylesheet.
- **Rejected:** the earlier Cloudflare-dashboard style (white cards on light gray, light only). A manual theme toggle is also left out for now (YAGNI); following the OS setting is enough.
- **Note:** layout inspiration only. No Tailscale logo, name, icons or other brand assets.

### D-16 — `agents` table has all M1 columns from the start; dev database is reset on schema changes · accepted · 2026-11-20
- **What:** `schema.sql` creates `agents` with every column M1 will use (`version`, `info_json`, `last_seen_at` included), even though enrollment fills only some of them. `CREATE TABLE IF NOT EXISTS` never alters an existing table, so during development a column added later means deleting `data/headnode.db`.
- **Why:** the first time the schema must change on a database that holds real data is the moment to add versioned migrations (D-05), not earlier. Until then the database only holds test hosts, so deleting it costs nothing. Putting the M1 columns in now avoids needing even that during M1.
- **Rejected:** writing a migration system now (YAGNI), or adding `ALTER TABLE` statements to `schema.sql` (they fail on the second run).
- **Consequence (groups):** `agents` has no `group_id` yet. Groups arrive in M2, and that is when the first real migration is needed if the database holds data worth keeping.

### D-17 — One control connection per agent: the newest wins · accepted · 2026-11-20
- **What:** if an agent connects while the server still holds a control connection for the same agent id, the server closes the old one and keeps the new one. The old connection's cleanup only removes the registry entry if it still points at that same connection.
- **Why:** after a network drop the agent reconnects within seconds, but the server may not notice the old connection is dead for up to 60 s (the heartbeat timeout). Refusing the new connection would leave the host offline for that whole minute. The newest connection is the one the agent is actually using.
- **Rejected:** keeping the old connection and refusing the new one (host looks offline until the timeout). Allowing several connections per agent (every later feature would have to decide which one to talk to).
- **Consequence:** two machines that share one `agent.json` (a cloned VM, for example) will keep kicking each other off. That is a real misconfiguration; the log line `agent online` repeating for one agent id is the symptom.

### D-18 — Agent system info is split into pure parsers, a Linux reader and a stub · accepted · 2026-11-20
- **What:** `agent/procfs.go` has functions that parse the *text* of `/proc` files and has no OS-specific code. `agent/sysinfo_linux.go` reads the files and calls `syscall.Statfs`. `agent/sysinfo_other.go` (build tag `!linux`) has stubs that return an error.
- **Why:** `syscall.Statfs` does not exist on Windows, so without the stub the agent package would not compile on the Windows laptop and `go vet ./...` / `go test ./...` would fail there. Keeping the parsers in a plain file means the logic that is easy to get wrong (CPU % from two samples, `/proc/meminfo` units) is tested on any OS.
- **Rejected:** `golang.org/x/sys` (a new dependency, and it does not remove the need for a Windows stub). Telling the owner to always set `GOOS=linux` when running `go vet` (easy to forget, and then the error message is confusing).
- **Relation to D-12:** this is the first OS-specific file split, forced by the development machine rather than by a Windows agent. A real Windows agent would replace `sysinfo_other.go`.

### D-19 — UI: one JS file, DOM built with text nodes, polling every 2 s, strict CSP · accepted · 2026-11-20
- **What:**
  1. `web/app.js` is the whole UI. The page is chosen from the URL hash (`#/` = Hosts, `#/hosts/<id>` = detail), and the file is read top to bottom.
  2. Elements are built with a small `h(tag, attrs, ...children)` helper. Strings become text nodes. Agent-supplied text (hostname, kernel, platform) is **never** put into `innerHTML`.
  3. The page asks the server for fresh data every 2 seconds and redraws only if something changed.
  4. The server sends `Content-Security-Policy: default-src 'self'; frame-ancestors 'none'` (since extended, D-28 and D-49) with the UI files, so web/ has no inline scripts or `style=""` attributes.
- **Why:** (2) A host's hostname is chosen by whoever controls that machine, so a hostname containing HTML must not be able to run script in an admin's browser. Building with text nodes makes this safe by construction instead of relying on remembering to escape. (3) 2 s polling meets the "host shows up within 2 seconds" goal with no server push code, and the load is tiny for an admin tool. (4) The CSP is a second wall behind (2). It is cheap now and painful to add after inline scripts exist.
- **Rejected:** a framework or a template library (D-06). Server push (WebSocket/SSE) for host status: more code, and not needed for the current goal. Hash routing is also the reason no server route is needed for the detail page.
- **Consequence:** xterm.js (M3) must be vendored as a file, which D-06 already requires. The 2 s poll is replaced only if it proves too slow or too heavy.

### D-20 — User passwords: bcrypt from `golang.org/x/crypto`; the CLI reads the password from stdin · accepted · 2026-11-20
- **What:** passwords are hashed with `bcrypt` (`golang.org/x/crypto/bcrypt`, default cost). Passwords must be 8 to 72 bytes: bcrypt reads only the first 72 bytes, so a longer password would be silently cut, and the code refuses it instead. Usernames are lowercased and limited to `a-z 0-9 . _ -`, 1 to 32 characters. `headnode user create` reads the password from stdin (prompted twice on a terminal, never a flag).
- **Why:** architecture.md §7 and D-09 already name bcrypt for human passwords. It is slow on purpose and salts each hash itself, which is what makes a stolen database hard to crack. `x/crypto` is maintained by the Go team and is the standard home of bcrypt. This is the project's third dependency, after `modernc.org/sqlite` and `coder/websocket`, and was approved by the owner on 2026-11-20.
- **Rejected:** PBKDF2 from the standard library (`crypto/pbkdf2`, no dependency, but much weaker against GPU cracking). Passing the password as a flag (visible in the process list and shell history).
- **Consequence:** the standard library cannot switch off terminal echo, so a password typed at the `user create` prompt was visible on screen. Superseded in part by D-21.

### D-21 — `golang.org/x/term` hides the password typed at `user create` · accepted · 2026-11-20 · supersedes the echo consequence of D-20
- **What:** `headnode user create` uses `term.ReadPassword`, so nothing is shown while the password is typed. When stdin is not a terminal (a pipe), it reads one plain line instead, so scripts keep working. A Ctrl+C handler restores the terminal before exiting.
- **Why:** the owner asked for it right after seeing the visible prompt. A password on screen ends up in scrollback and over-the-shoulder. `x/term` is maintained by the Go team, small, and works on Windows and Linux. This is the project's fourth dependency.
- **Rejected:** hand-written echo switching with `syscall` (different code for Windows and Unix, build tags, easy to get wrong). Leaving it visible.
- **Consequence:** `term.ReadPassword` leaves echo off if the process is killed in the middle of a prompt, so the Ctrl+C handler in `cmd/headnode/user.go` restores the terminal state. A `kill -9` cannot be caught; on Linux `reset` fixes the terminal.

### D-22 — API is default-deny, and the Origin check refuses a missing Origin · accepted · 2026-11-20
- **What:** all authenticated routes are registered on an inner mux, and the whole inner mux is wrapped by `requireLogin`. The outer mux has exactly four public things: the web page files, the agent endpoints (own credentials), `POST /api/login`, and nothing else under `/api/`. `POST`/`PATCH`/`PUT`/`DELETE` on the guarded routes, and login itself, also require an `Origin` header whose host equals the request's `Host`. A request with no `Origin` is refused.
- **Why:** CLAUDE.md says every endpoint except login and enroll must check authentication. Checking per handler means one forgotten line makes a public hole. With the wrapper, a new route is protected unless someone deliberately registers it on the outer mux, and unknown `/api/*` paths answer 401 too instead of leaking that they do not exist. Browsers always send `Origin` on a POST, so a missing one means the caller is not a browser tab, and cookie authentication must not apply.
- **Rejected:** a `requireLogin(handler)` call on every route (easy to forget). Checking `Referer` (browsers may omit it). CSRF tokens in forms (more moving parts than the Origin check plus `SameSite=Lax`, which together cover the same attacks for a JSON API).
- **Consequence:** the static page files are public. They contain no data, and the login page has to load before anyone can log in. The mux needs one line per HTTP method for the guarded prefix, because a pattern without a method would conflict with `GET /`. Clients that use `Authorization: Bearer` (hnctl, M5) will skip the Origin check, as protocol.md already says.

### D-23 — Login sessions: random token, hash stored, 7 days; `Secure` cookie only over HTTPS; per-address failure delay · accepted · 2026-11-20
- **What:** a login creates a random 256-bit token. The cookie `hn_session` holds it, the `web_sessions` table holds only its SHA-256 (D-09). It expires 7 days after login, with no renewal on use. The cookie is `HttpOnly` and `SameSite=Lax`, and `Secure` when the request arrived over HTTPS (directly, or through a proxy on this machine sending `X-Forwarded-Proto: https`). A wrong username still costs one bcrypt comparison, against a dummy hash. Failed logins are counted per client address in memory: 3 free, then a growing wait (1 s, 2 s, 4 s … 15 min).
- **Why:** stored hashes mean a leaked database cannot be used to hijack a logged-in browser. `HttpOnly` keeps an injected script from reading the cookie. A fixed lifetime is the easiest rule to explain and to test. `Secure` must not be forced, because development runs on plain `http://` and the browser would silently drop the cookie, but it must be on in production behind Caddy, hence the proxy check. The dummy comparison keeps "no such user" from answering faster than "wrong password", which would reveal which usernames exist. The growing wait turns online guessing from thousands per minute into about 15 per hour per address, and a person who mistypes twice never notices it.
- **Rejected:** sliding expiry (harder to reason about, a stolen cookie could live forever). JWTs (cannot be revoked on logout without a server-side list, which is a sessions table anyway). A fixed lockout after N failures (lets an attacker lock a real user out; a growing wait does not lock anyone out for long). Trusting `X-Forwarded-For` from anyone (a client can write anything there, so it is only believed from a proxy on this machine, and only its last entry).
- **Consequence:** the limiter is in memory, so a server restart forgets it. Sessions survive a restart because they are in the database. The limiter tracks addresses, not usernames, so someone with many addresses can try a few passwords from each. That is accepted for now. The audit log records failed logins by address (D-24).

### D-24 — Permissions: one `can()`, hidden hosts answer 404, ungrouped hosts are admin-only, audit writes never block, dev database reset · accepted · 2026-11-20
- **What:**
  1. `can(user, host, action)` in `server/permissions.go` is the only place that decides whether a user may act on a host. The role table from architecture.md §6 is data (`rolePermissions`), and unknown roles or actions get `false`. Admins pass everything. Everyone else needs a role in the host's group.
  2. The host list is filtered with the equivalent SQL (`group_id IN (SELECT group_id FROM group_members WHERE user_id = ?)`), because asking `can()` once per host would be one query per host. A test checks that the two always agree.
  3. A host the user may not see answers `404`, exactly like a host that does not exist.
  4. A host in no group (`agents.group_id` is NULL) is visible to admins only. Hosts enrolled from the command line start this way.
  5. `audit()` records one row per action. If the write fails it logs through `slog` and the action still goes through.
  6. `groups`, `group_members`, `audit_log`, `agents.group_id` and `enroll_tokens.group_id` are all in `schema.sql` now, and the development database must be deleted once (the D-16 consequence).
- **Why:** (1) "All checks go through one function" is the only way to audit permissions by reading code. Putting the table in data makes it readable next to architecture.md and easy to test completely. (3) A `403` would confirm that the host exists. (4) Without it we would need a rule for "no group", and "only admins" is the safest one that needs no extra concept. (5) An admin should not be locked out of fixing something because the log disk is full, and the `slog` line is still a record. The cost is that a crashed audit write can leave an action unrecorded, which is accepted for a self-hosted tool at this size. (6) Putting every M2 column in at once means one reset instead of one per slice.
- **Rejected:** checking roles inline in each handler (nobody can audit that). Failing the action when the audit write fails (safer on paper, but makes the audit log a single point of failure for the whole dashboard). `403` for hidden hosts. Writing a migration system now: the database only holds test hosts, and migrations are added the first time real data would be lost (D-05).
- **Consequence:** deleting `data/headnode.db*` means re-creating the admin user and re-enrolling hosts once. After this, a schema change to an existing table needs a real migration. The groups feature is only usable together with the move-host action in the next slice, since new hosts start ungrouped.

### D-25 — Host admin actions: admin-only, PATCH with three-way `group_id`, delete cuts the connection, token reply shows the manual enroll command · accepted · 2026-11-20
- **What:** renaming, moving and deleting a host, and creating group enroll tokens, are admin-only. `PATCH /api/hosts/{id}` takes `name` and/or `group_id`, and `group_id` can be absent (keep), `null` (no group) or an id (move there). The whole request is validated before any change and applied in one transaction. `DELETE` removes the row first and then closes the live connection. A real move or rename is audited, a no-op is not. The token reply's `install_command` is the manual enroll command until the installer exists (M6).
- **Why:** moving a host changes who can see it, and architecture.md §6 gives user, group and token management to admins only, so the host actions follow the same rule instead of inventing a middle role. A plain integer cannot tell "leave the group alone" from "remove the group", and a wrong guess there would silently hide a host, so the field is read as raw JSON. Validate-then-apply keeps a half-good request from leaving the host half-changed. Deleting the row first closes the window in which a still-valid agent could reconnect. Not auditing no-ops keeps the log readable. The UI needs a stable field name for the command, so the field keeps its documented name and only its content changes in M6.
- **Rejected:** letting operators rename hosts in their own group (a second kind of permission to explain, for little gain). A separate `/api/hosts/{id}/group` endpoint (more routes for the same thing). Closing the connection first, then deleting.
- **Consequence:** deleting a host is final: the agent's `agent.json` becomes useless and the agent keeps retrying with 401 until it is re-enrolled. The audit log keeps the host's id and name after the delete.

- **Update (same day):** the token route is `POST /api/enroll-tokens` with an optional `group_id`, replacing `POST /api/groups/{id}/enroll-tokens`. The Hosts page lets the admin choose "No group" (the default choice), and the group page's "Add host" skips the choice and creates the token for that group at once. One route with a nullable field is simpler than two routes for the same action, and an ungrouped token is the safer default: a host that lands in the wrong group is visible to people who should not see it, an ungrouped one only to admins.

### D-27 — Sessions: opaque relay run by the browser's handler, single-use user-bound ids, pings, close pass-through · accepted · 2026-11-20
- **What:** `relay()` copies WebSocket messages between two connections without reading them. The browser's handler runs it. The agent's handler hands over its connection and waits until the session is over, so exactly one goroutine copies bytes. A session id is 128 random bits, valid for one browser and one agent attach, and bound to the user who created it (and the agent it was opened on): anyone else gets 404, admins included. A 15 s countdown from creation cancels a session nobody paired. The relay pings both sides every 30 s. When one side ends, the other gets the same close code and reason, and the relay closes the surviving side first (a close frame), cancels afterwards.
- **Why:** an opaque relay is the whole reason shell, files and tunnel can share one mechanism (D-02), and it keeps the server from ever parsing terminal bytes. One relaying goroutine avoids two copiers racing on the same connections. Binding the id to the user means a leaked id is useless to another logged-in person. Pings are how a vanished peer (a laptop that slept, a pulled network cable) is detected: without them the session, and the shell on the host, would live forever. Passing the close code and reason through lets the browser show "cannot start a shell: …" instead of a bare disconnect. Cancelling the context before sending the close frame would make the library drop the connection without a goodbye, hence the order.
- **Rejected:** a session id any logged-in user can attach (guessing is hard, but a leak would then be fatal). Letting both handlers copy (two goroutines per direction, racy shutdown). Detecting dead peers only through TCP (can take hours).
- **Consequence:** there is no per-host or per-user limit on concurrent sessions yet, so one operator can start many shells. A fixed limit is a small addition when it matters. Closing the browser tab ends the shell because the close propagates: browser, relay, agent, PTY hangup. Background jobs that a shell started in their own process groups may outlive it.

### D-28 — Terminal dependencies: `creack/pty` for the agent, xterm.js vendored, and `style-src 'unsafe-inline'` in the CSP · accepted · 2026-11-20
- **What:** the agent uses `github.com/creack/pty` to start the shell in a pseudo-terminal (fifth dependency, already named in architecture.md and D-12). The browser uses xterm.js 5.5.0 and its fit addon 0.10.0, copied into `web/vendor/` (D-06, with a README that pins versions and gives the download commands). The Content-Security-Policy changed from `default-src 'self'` to `default-src 'self'; style-src 'self' 'unsafe-inline'; frame-ancestors 'none'`.
- **Why:** a PTY is what vim and htop need (size, raw mode, cursor control), and `creack/pty` is the standard, small way to get one on Linux without hand-writing ioctls. xterm.js builds `<style>` elements at run time to size and color the terminal, and the strict policy blocks that, so styles must allow inline. Scripts stay locked to our own files, which is where the protection against injected code lives (D-19). The files are vendored so the dashboard needs no internet and a CDN cannot change what runs in the page.
- **Rejected:** writing the PTY handling with raw syscalls (more code, easy to get wrong, and the dependency is small). Loading xterm.js from a CDN. A style nonce (xterm.js does not support passing one). Keeping the strict style policy and a broken terminal.
- **Consequence:** the page now accepts inline styles. An attacker who could inject markup could restyle the page, but still not run script. Updating xterm.js means editing `web/vendor/README.md` and downloading the files again.

### D-26 — Admin UI: native `<dialog>`, dialogs outside the redrawn area, admin controls hidden for convenience only · accepted · 2026-11-20
- **What:** pop-up forms use the browser's `<dialog>` element (`showModal()`), created in `app.js` and attached to `<body>`, not inside `#view`. Every dangerous action (delete host, remove member) goes through a confirm dialog that names the object. Admin buttons and the Admin sidebar section are shown only when `/api/me` says `is_admin`, and nothing relies on that.
- **Why:** `<dialog>` gives focus trapping, Esc to close and the dimmed backdrop with no code and no library (D-06). The page redraws whenever data changes, so a form inside `#view` could be wiped while someone types. Hiding admin controls keeps the UI quiet for people who cannot use them, but the server is the security boundary: every admin route is `adminOnly` and tested (D-22, D-24).
- **Rejected:** a modal built from divs (focus handling and Esc would be our code). Putting forms inline in the page (wiped by the redraw). Treating the hidden buttons as protection.
- **Consequence:** below 1024 px the sidebar is hidden (design.md), so on a narrow screen there is no navigation to the Admin pages yet. A top bar for small screens is still to do.

### D-29 — Hosts table: no Version column, WAN address from the server's view of the connection, Shell button from `can_shell` · accepted · 2026-11-20
- **What:** the Version column left the Hosts table (the agent version and kernel stay on the host page). The Addresses cell shows the host's own addresses, then `WAN <ip>`. The WAN address is what the server sees when the agent's control connection arrives: it is stored on every connect (`agents.wan_addr`) and returned as `wan_addr`. A **Shell** button appears on a row when the host is online and the API says `can_shell` for the current user.
- **Why:** every host runs the same agent version until auto-update (A3) exists, so the column repeated one value on every row. The agent cannot know its public address (it may sit behind NAT), and one it reported about itself could not be trusted, so the only honest source is the other end of the connection. The server finds that address with `clientIP`, the function login already uses, so `X-Forwarded-For` is believed only when the request came from the proxy on this machine, and then only its last entry. Without that rule anyone could put any address in the header: an agent could claim to be somewhere else, and a login attacker could rotate fake addresses past the rate limit. `can_shell` is computed from the same role table as `can()` and a test keeps the two equal, so a button is never offered that the server would refuse.
- **Rejected:** having the agent look up its public IP on an outside service (a dependency on a third party, and the agent could lie). Keeping the Version column "for when it differs". Asking `can()` once per host for the button (one query per host on every 2-second poll).
- **Consequence:** `wan_addr` is the address of the last connect and stays when the host goes offline. On a local test it is `127.0.0.1`. If the server sits behind a proxy that is not on the same machine, the address is that proxy's. A refused terminal (for example a role change after the page loaded) is still answered by the server, since the button is only a convenience.

### D-31 — File sessions: the server hands the agent a read-only flag, and individual file operations are not audited · accepted · 2026-11-20
- **What:** a `files` session needs `files_read`. The server works out whether the user also has `files_write` and puts `{"readonly": true|false}` in the `open` message. The agent refuses `mkdir`, `rename` and `delete` in a read-only session. The browser's own `params` are ignored. The audit log records that a files session was opened (with its read-only flag) and when it closed, but not each operation inside it.
- **Why:** the relay copies messages without reading them (D-27), so the server cannot look at a `delete` request and ask "is this user allowed?". The decision has to be made once, at the start, by the one party that knows the user's role, and carried to the agent through the channel only the server controls. A viewer then gets a session that cannot change anything, whatever their browser sends. Parsing every request in the server would give per-operation checks and a full audit trail, but it would make the relay know each session kind's protocol, which is the thing D-02 and D-27 avoid.
- **Rejected:** having the server read and filter files requests (a relay that understands one kind of session is the start of a relay that understands them all). Trusting the browser to say which operations it will use. Two session kinds (`files` and `files-readonly`) for the same protocol.
- **Consequence:** an operator's `mkdir`, `rename` and `delete` inside a session are not individually in the audit log: only "session opened, read-write, by whom, on which host, for how long". The agent's own log (slog) can record operations if that is needed. This weakens the architecture's "audit file operations" goal for file changes. Downloads and bulk sends (next slices) go through the server's own endpoints and are audited one by one. If per-operation audit becomes a requirement, the files kind would need a small, explicit hook in the relay, decided then. *(Follow-up: D-37 added the audit without a hook in the relay.)*

### D-32 — Downloads: the server is the browser's stand-in, streams in 64 KB chunks, cuts the connection on a mid-stream failure · accepted · 2026-11-20
- **What:** `GET /api/hosts/{id}/download` asks the agent for a `download` session and then reads the file's frames from the agent's WebSocket and writes them to the HTTP response one at a time. It sends `Content-Length` from the agent's header frame. If the agent fails before the first byte, the server answers with a real HTTP status (404, 403, 400, ...). If it fails after, the server aborts the connection (`http.ErrAbortHandler`). A browser that stops reading for a minute is dropped. The start is audited as `file_download`.
- **Why:** nothing is stored or collected, so a 1 GB file costs about one chunk of memory and no disk, and a slow browser slows the agent through ordinary TCP back-pressure (the roadmap's "without the server's RAM spiking"). Using the same session mechanism as the shell means the agent side needed one small function and the pairing code was reused. The agent sends no header when the file cannot be read, which keeps "the file is not there" a clean 404, since the status line has not gone out yet. After it has, no status can change, and a short body that looks finished is worse than a visible failure: that is why the connection is cut, and why `Content-Length` is sent, so the browser can tell.
- **Rejected:** saving the file on the server first, then serving it (disk, delay, cleanup). Buffering it in memory. A header-less stream with chunked encoding (a cut-off looks like a complete file). Letting the browser attach to the session itself (a second, different protocol for the same bytes).
- **Consequence:** a download holds one connection to the host for its whole duration, and there is no resume or range support yet. Only regular files are sent, so special files such as devices are refused. The audit entry records the start with the size, not whether it finished.

### D-33 — Bulk send: content-addressed uploads, status per host in memory, an agent may fetch only what it was told to · accepted · 2026-11-20
- **What:** an upload is streamed to disk while its SHA-256 is computed and stored as `data/files/<sha256>`, with a row in `files` (migration 2) for the name and owner. `POST /api/transfers` checks everything first (write permission on every target, ownership of the file, the shape of the destination and the mode), then sends each online agent a `fetch` with the file's hash and size. The agent downloads to `<dest>.part`, verifies size and hash, applies the mode and renames over the destination. Status per host is kept in memory for a day. `GET /agent/files/{id}` serves a file only to an agent that has a *pending* transfer of that file. Modes above `0777` are refused. A host that disconnects with a transfer pending is marked failed.
- **Why:** streaming means a 15 MB program or a 4 GB archive costs the same memory. Naming files by hash stores identical uploads once and gives the agent something to verify against. The rename is the whole point of `.part`: the destination is either the old file or the complete new one, and a running program can be replaced (writing into it fails). Checking every host before sending anything avoids a half-started send that the person would have to untangle. The pending-transfer rule matters because every enrolled host has valid credentials: without it, any host could read every file anyone ever uploaded, by guessing or learning an id. Refusing setuid bits keeps this from becoming an easy way to plant a program that runs as someone else.
- **Rejected:** a queue for offline hosts (more state, and D-03 chose "fail now, send again"). Keeping transfer status in the database (survives a restart, but the final results are in the audit log). Streaming the upload from the browser through the server into each agent (D-03). Letting any logged-in user send any uploaded file (file ids would become capabilities).
- **Consequence:** uploaded files are never deleted automatically (D-38 added a manual delete for admins), and there is no disk quota. If the server restarts mid-transfer the status is lost but the audit log keeps what finished. If an agent's control connection drops while it works, the transfer shows as failed although the file may have arrived. The agent reports on the connection it was told on, and a reconnect does not carry the result over. Two transfers to the same path on the same host at the same time share one `.part` file and can break each other. The folder of the destination must already exist.

### D-34 — The temporary file of a fetch has a random name; transfers can be listed; the page learns permissions from the API · accepted · 2026-11-20 · refines D-33
- **What:** the agent writes a fetch to `<name>.<random>.part` in the destination's folder (`os.CreateTemp`) instead of a fixed `<dest>.part`. `GET /api/transfers` lists the user's transfers (everyone's for an admin). `GET /api/me` returns `can_upload` and every host returns `can_files_write`, computed from the same role table as `can()` with tests that keep them equal (like `can_shell`). The Transfers page, its detail page and the Send file dialog are built on these.
- **Why:** a fixed `.part` name made two transfers to the same path share one file, and left a stale file behind when an agent was killed half way: D-33 listed both as consequences. A random name removes them, and it makes it possible to test "several hosts at once" with several agents on one machine, where every agent writes the same path. The list exists because status lives in memory only (D-03): without it, a person who closed the tab could never find a transfer again. The page needs to know what the user may do to decide what to offer, and the server stays the only place the rule is decided.
- **Rejected:** a lock per destination path (more state, and it does not help when two different machines share a network folder). Keeping the fixed name and documenting the limit. Having the page work out permissions from roles (a second copy of the rule).
- **Consequence:** an agent that is killed in the middle of a fetch can leave a `<name>.<random>.part` file in the destination folder. It is not cleaned up automatically. Several agents on one machine writing the same destination at once all succeed, and the last rename wins, which is harmless because the content is identical.

### D-35 — Tunnel targets are limited to the host itself · accepted · 2026-11-20
- **What:** a `tunnel` session may only connect to `localhost` or a loopback address (`127.0.0.0/8`, `::1`) on the host, on a port from 1 to 65535. The server refuses anything else with `400`, `hnctl` refuses it before connecting, and the agent checks again before it dials. A tunnel needs the same role as a shell (`operator`).
- **Why:** a target the user chooses is an address the agent will connect to from inside the host's network. Unrestricted, every operator could use a host as a stepping stone to anything that host can reach: the router's admin page, a database on another machine, the cloud metadata service at `169.254.169.254`. That is far more than "open a shell on this host", which is what the role grants. Limiting targets to loopback still covers the point of the feature (SSH, a web panel, a database on the host itself, reached from behind NAT), and keeps the reach of a tunnel equal to the reach of a shell. The agent repeats the check because it is the one that dials: it must not depend on the server, or on a client, being honest.
- **Rejected:** any target (a network pivot by default). An allow-list per host in the database (more concepts, and nothing needs it yet). Trusting only the server's check.
- **Consequence:** a device on the host's LAN (a camera, a router, a NAS) cannot be reached through the host yet. That is a deliberate next decision, for example an explicit per-host list of extra targets set by an admin, or the HTTP relay (B7) for web interfaces. It should be added knowingly, not by loosening this check.

### D-36 — hnctl uses bearer tokens, which need no Origin check · accepted · 2026-11-20
- **What:** `POST /api/login` with `"client":"cli"` answers with a token in the body and sets no cookie. The token is an ordinary login session (same table, same 7 days, stored hashed), sent as `Authorization: Bearer <token>`. Requests that carry it skip the `Origin` check, and so does that login request. A request with an `Authorization` header is judged on it alone and never falls back to a cookie. `hnctl` keeps the token in a `0600` file in the user's config folder, and `hnctl logout` deletes the session on the server too.
- **Why:** a command-line program has no browser cookie jar and sends no `Origin`. The `Origin` check exists because a browser attaches cookies to requests that another website triggers. A bearer token is only attached by code that was given it, so there is no such forged request to defend against, and requiring `Origin` would only force the program to send a made-up one. Judging an explicit `Authorization` header on its own prevents mixing the two: a bad token with a good cookie must not succeed, or the cookie's lack of Origin protection could be exploited by attaching a junk header. The login rate limit and the audit log apply to command-line logins exactly like browser ones.
- **Rejected:** a separate kind of API key (a second token system to build and explain). Sending a fake `Origin` from `hnctl`. Long-lived tokens that never expire.
- **Consequence:** whoever has the token file can act as that user for up to 7 days, so the file is private to its owner and `hnctl logout` revokes the token. On a shared computer, use `logout`. There is no list of a user's tokens or way to revoke one from the dashboard yet.

### D-37 — File changes are audited from the agent's reports, attributed through the session record · accepted · 2026-11-20 · follows up D-31
- **What:** after a files session runs a `mkdir`, `rename` or `delete`, the agent sends a `file_change` message on its control connection: the session id, the operation, the path (and `to`, `recursive`), whether it worked, and a short error if not. The server looks the session up, requires that it was opened on the reporting agent, takes the **user from the session record**, and writes `file_mkdir`, `file_rename` or `file_delete` to the audit log, failures included (`FAILED: <error>`). Reads (`list`, `stat`, `home`) and changes a read-only session refused are not reported. The relay is unchanged. Because the report travels on a different connection from the relay, it can arrive after the session ended, so the server keeps the owner (user and host) of an ended files session for 5 minutes, cleaned up whenever another session ends.
- **Why:** D-31 left per-operation audit open and warned that it might need a hook in the relay. It does not. The agent is the one party that sees both what was asked and what happened on the disk, and the server is the one that knows who the session belongs to, so each says only what it knows: the agent never claims a person, the server never parses a request. That keeps D-02 and D-27 true: the relay still copies bytes and knows nothing about files. Reporting after the operation means the log shows the outcome, and a failed attempt (an operator trying to delete `/etc/shadow`) is the line worth reading. Requiring the session to belong to the reporting agent means an agent can only add lines about its own host, under people who really opened a session on it. The 5-minute memory exists because the final report of a session can lose the race against the browser closing; without it the last change of a session would be dropped, or audited under nobody.
- **Rejected:** parsing requests in the relay (D-31). Having the agent send the user's name (the agent cannot know it, and would be believed). Auditing before the operation runs (records intentions, not what happened). Keeping every finished session forever (grows without bound). Reporting reads too (a line per directory opened buries the lines that matter; downloads are already audited by the server). Auditing the shell the same way (the shell is arbitrary commands, not a few known operations).
- **Consequence:** the log trusts what the agent says about the change itself. That is acceptable: an agent that lies already controls its own machine, and it cannot name another host or an unrelated user. A report lost on a broken control connection is not retried (the agent logs a warning), so this is a good record, not a guaranteed one. Only the Files tab is covered: commands typed in a shell, and uploads (`fetch`, audited by the transfer entries), are not seen here. A report that arrives more than 5 minutes after the session ended is dropped with a warning in the server log.

### D-38 — Uploads are deleted by hand, by an admin; a shared blob stays; a file in use is refused · accepted · 2026-11-20 · follows up D-33
- **What:** `GET /api/files` lists every upload and `DELETE /api/files/{id}` deletes one, both admin only (a new **Uploads** page under Admin; the delete is Origin-checked like every change and audited as `upload_delete`). Two uploads of the same bytes are two rows with one blob on disk (`data/files/<sha256>`), so the blob is removed only when no other row has the same hash. A file that a transfer is still waiting on (at least one host has not answered) is refused with `409`. A transfer that has been unanswered for more than an hour no longer counts. One mutex makes "store a blob and record its row" and "delete a row and maybe its blob" run one at a time.
- **Why:** D-33 left uploads on disk forever. A person can only delete what they can see, and no page listed uploads, so the list comes with the delete. Hash-named blobs are why sharing matters: deleting by file name would break a second upload that points at the same bytes. Refusing a file in use keeps an agent's `fetch` from failing half way. The one-hour limit exists because a pending status only ends when the host answers or disconnects: an old agent that ignores `fetch` (it happened) would otherwise lock its file against deletion for good. The mutex closes a small race: an upload sees the blob exists and skips writing it, then a delete removes it before the upload's row is saved, leaving a row with no file. Only admins delete because it is the only way to free disk space and affects other people's uploads.
- **Rejected:** automatic expiry or a cleanup job (a background task and a retention policy nobody has asked for yet; manual delete is enough to start). Letting operators delete their own uploads (more rules to check, and the disk is the admin's concern). Deleting the blob regardless and failing later fetches (a transfer failing for no visible reason). Reference counts stored in the database (the count of rows with the same hash is the truth and cannot drift).
- **Consequence:** disk is freed only when an admin remembers to do it. A transfer started in the instant between the in-use check and the delete fails cleanly (the agent's download gets `404`), it does not corrupt anything. Past transfers keep showing the file's name after it is deleted, but sending it again is `404`. If removing the blob from disk fails, the row is already gone: the server answers `500` and logs it, and the orphan blob has to be removed by hand.

### D-39 — File manager: copy, chmod and props are agent operations, with limits; the rest is the page · accepted · 2026-11-20 · extends D-31, D-37
- **What:** three operations join the files session. `copy` (a file, or a folder with everything in it, to a path that does not exist), `chmod` (the nine rwx bits of one item) and `props` (size, mode, owner, group, a folder's total size). `copy` and `chmod` are changes: refused in a read-only session, reported to the server and audited (`file_copy`, `file_chmod`, D-37). `props` is a read, like `stat`, and is not audited. A folder walk (the size of a folder, or the count before a copy) looks at 100,000 entries at most: `props` then says the numbers are partial, and `copy` is refused before it writes anything. Everything else added to the Files page is the page alone, and asks the host nothing new: sorting by name, size or date, the filter box, the hidden-files switch, ticking several items, Move (the existing `rename` into another folder), Copy path, renaming in the row, and the folder picker. A batch (delete, move or copy of several items) is one request per item, so the host reports and the server audits each one. An upload that meets an existing name now keeps both: the page asks the host (`stat`) for the first free name and uploads as `name (1)`.
- **Why:** the host is the only one that can copy a folder (the relay does not read a session, D-27), and a copy done as many small browser-side requests would be slow and could stop half way with no way to undo. Like `rename`, `copy` never overwrites: the page picks a free name, and the agent refuses if something appeared meanwhile, because a silent replace of someone's file is the worst surprise a file manager can give. Links are copied as links: following them would let a link inside a folder pull a file from anywhere into the copy. A failed folder copy removes what it made (it created the destination itself, so it is safe to remove). `chmod` accepts only the nine bits, like a sent file (D-33): the file manager must not be an easy way to plant a setuid program, and it does not recurse, because a recursive chmod of a mistyped path is hard to undo. The limit on the walk exists because "how big is `/`?" would keep the host busy for minutes, and the session handles one request at a time. The filter, sorting and the hidden-files switch work on the listing the page already has, so they are instant, and they only ever change what is shown. What is ticked is always on screen: an item that a filter hides is un-ticked, so a delete cannot reach something you cannot see. Asking `stat` for a free name instead of reading the folder listing keeps the upload right in a folder too big to list completely (the listing stops at 2000).
- **Rejected:** a recursive chmod (too easy to do damage with). Overwriting on copy or upload with a confirm (a click-through habit loses files). A `move` operation (`rename` already does it, and the host reports it the same way). Doing the copy as a list of single-file requests from the browser. Sorting and filtering on the host (a request for every keystroke).
- **Consequence:** a copy or a size count of a big folder blocks that session for as long as it takes (the other requests of the same Files tab wait; a second tab has its own session). A host with an older agent answers "unknown operation" to the new buttons: the agent version is now 0.4.0 and the host page shows it. Move is `rename`, which the operating system refuses between two filesystems (`invalid cross-device link`): the page shows that error and does not work around it (a copy then delete) yet. A free name found by `stat` can be taken by someone else before the transfer lands: a move or a copy is refused then, but an upload still replaces (D-33). The listing is cut at 2000 entries, so sorting, filtering and Select all work only on those.

### D-40 — Agent programs are built by a script and served from a folder, with no login · accepted · 2026-11-20
- **What:** `scripts/build-agents.ps1` (and `.sh`) cross-compile `headnode-agent` for `linux/amd64` and `linux/arm64` into `dist/`, as static programs (`CGO_ENABLED=0`, `-trimpath -s -w`). The server serves them at `GET /download/headnode-agent-{os}-{arch}` from the folder given with `-agents` (default `dist`). Only names on a fixed list are served. The route needs no login.
- **Why:** an install command (the next M6 slice) runs on a host that has no credentials yet, so the download cannot require any. The program holds no secret: what makes a host belong to the server is the enroll token, which is checked separately and expires. A folder of files beside the server is the smallest thing that works, and building them by hand needs only the Go toolchain you already have. The fixed list means the name from the URL can never reach another file, and adding a platform is one line plus one build. Static builds mean one file per architecture runs on any Linux, whatever its C library. `Cache-Control: no-cache` and no embedding in the server binary mean you can rebuild the agent without rebuilding or restarting the server.
- **Rejected:** embedding the binaries in the server with `go:embed` (the server would need the agents built first, grow by their size, and be rebuilt for every agent change). Having the server run `go build` itself (the server machine would need a Go toolchain and the source). Requiring a login or the enroll token to download (the install command could not carry it safely, and the program is not a secret). A checksum file next to each program (over HTTPS it adds nothing a person can check by hand, and the enroll step already proves who the server is).
- **Consequence:** whoever runs the server must run the build script after changing the agent and put the result in the agents folder, or new installs get an old agent. Anyone who can reach the server can download the agent program, which is already public source. Windows and macOS agents are not offered (D-12).

### D-41 — File manager, third round: zip folders, a text editor, host-to-server pull, drag and drop · accepted · 2026-11-20 · extends D-32, D-33, D-39
- **What:** (1) A `download` of a folder is sent as a zip archive, built while it is sent, with an unknown size (-1) in the header. (2) Two operations, `read` and `write`, for a text editor in a dialog: files up to 512 KB, valid UTF-8, no NUL. `write` needs the `version` that `read` returned and is refused if the file changed since. A save is a change (refused in a read-only session, reported, audited as `file_write` with its size and never its text). A read-only session can *view*. (3) `POST /api/hosts/{id}/pull` copies a file from a host to the server's uploads, so "Send to hosts…" can use the existing bulk send. (4) Dropping files from the computer onto the page uploads them, and dragging rows onto a folder (or a folder of the path bar) moves them. 2 and 4 add nothing to the relay; 3 reuses the `download` session; the relay's message limit went from 1 MB to 4 MB.
- **Why:** a zip built on the fly needs no disk on the host and no memory on either side, and it is the same session as a single file, so no new session kind was needed: the header's "size unknown" and the server's chunked response and abort-on-failure were already in D-32 for exactly this. The agent skips what it cannot read and says so in a `SKIPPED.txt` inside the archive, because an archive that quietly lacks files is worse than no archive. Links are not followed, for the same reason as in copy (D-39). The editor's version check exists because a save is a blind overwrite otherwise: if an admin edits `nginx.conf` in the browser while someone else changed it on the host, the second save must not erase the first. The version is the modification time and size, not a hash, so a save does not read the file again. The write goes into the file itself, not a new file renamed over it, so the owner, the mode and links stay as they are: the files this is for are small config files that belong to some service. The 512 KB cap keeps a save well inside one message, and "not valid UTF-8, or has a NUL byte" keeps the text box from damaging a binary file when it is saved. Windows line ends are put back on save, because a browser text box hides them. A save is audited by size only: the content may be a password. Pulling a file reuses the `download` session, so the agent needed nothing new, and it is checked as both a download (`files_read` on the host) and an upload (the right to upload), since it is both. Pull fails if the file's size changes while it is copied, rather than storing a torn copy of a log. Drag and drop is only a different way to start the upload and move that already exist, with the same checks.
- **Rejected:** a new `archive` session kind (the `download` kind already fits). Zipping into a temporary file first (disk on the host, and the person waits for the whole zip before the first byte). Following links into the archive. A blind overwrite on save, or locking the file (a lock nobody releases when a tab is closed). Replacing the file by a rename on save (changes the owner when the agent is root). A bigger editor with syntax colors (a dependency, and not needed to fix a config line). Creating new files from the editor. Having the browser send the folder-to-server upload (the server can already pull from the host).
- **Consequence:** a crash during a save can leave a half-written file; the file manager is for small files, so this is accepted (an editor on the host has the same risk). The version check cannot see a change that keeps both the size and the modification time to the nanosecond. The zip of a folder with 100,000 or more entries fails; the folder's own size is not shown before it starts. A pulled file stays on the server as an upload until an admin deletes it (D-38), even if the person closes the Send dialog without sending. Dropped files get mode `0644`; the Upload button has the mode field. Dragging works with a mouse; there is no touch support yet.

### D-42 — Several files per upload or send: one request chain per file, sequential, no new endpoint · accepted · 2026-11-20 · extends D-33, D-41
- **What:** the file manager's Upload dialog and the Transfers page's Send files dialog accept several files. Each file goes through the same steps as a single one (upload to the server, then a transfer), one file after another. Send files makes one transfer per file, with the same hosts, folder and mode, and keeps each file's own name when there are several. The page changes only; the server and the agent are unchanged.
- **Why:** a transfer is one file to several hosts (D-33), with its own status page and its own audit lines. Making it hold a list of files would change the model, the API, the status page and the audit log, to save a loop. One transfer per file keeps every existing guarantee (per-host status, the `.part` file renamed into place, a checksum per file) and an audit trail that says which file went where. Sequential, not parallel: it is easy to follow ("3 of 8"), puts one upload at a time on the person's connection, and a failure has a single clear place. In the file manager a failure does not stop the rest, because the files that worked are already in place and nothing is lost by going on; in Send files, a failure stops the loop and leaves only the unsent files selected, because pressing Send again must not start the same transfers twice.
- **Rejected:** one transfer holding several files (a new data model and API for the same result). Uploading in parallel (harder to read, and a failure is harder to place). A folder picker that keeps the folder's structure (needs `mkdir` on every host, which a send does not have; the Files tab could, and this is for later). A new `POST /api/files` that takes several parts (the browser can just call it several times).
- **Consequence:** sending 50 files to 10 hosts makes 50 transfers, each its own row on the Transfers page. A file that is large or slow delays the ones behind it. Sending several files does not take a whole folder with its subfolders: files are sent flat into one destination folder.

### D-43 — Sending a whole folder: zip it, send it with `extract`, unpack it carefully on the host · accepted · 2026-11-20 · extends D-33, D-41, D-42
- **What:** "Send to hosts…" in the file manager works on several items and on folders. Every item is copied from the host to the server one after another (`pull`); a folder arrives as a zip (the same archive a folder download makes) and is stored as an upload. The Send dialog then makes one transfer per item, and an archive is sent with a new `extract` flag: `dest_path` is an existing folder, and the agent unpacks the archive inside it. The folder appears under its own name, with every file's mode. The unpack is defensive: all paths are checked before anything is written (absolute, `..`, backslash, links and special files refuse the whole archive), entry count and unpacked size are limited and the size is enforced while writing, everything goes to a staging folder first, and top-level items are moved in only if none exists yet. The "Clear" button of the selection bar was removed (unticking, or the header checkbox, already does that).
- **Why:** a folder can have thousands of files, and a transfer is one file to several hosts with its own status page (D-33): one transfer per file would make thousands of rows and thousands of uploads, and sending a file needs its folder to exist, which a plain send cannot create. One archive is one upload, one transfer, one checksum, one audit line, and it keeps the structure and the modes. It reuses what exists (the zip a download makes, the pull of D-41, the fetch with its `.part`, checksum and error reporting), so the new code is only the unpack. The unpack is where the risk is: an archive is the classic way to write outside the folder you meant ("zip slip"), to plant a link that a later file is written through, or to fill a disk. The agent is the last line and does not trust the server's archive: refusing before writing anything means a hostile archive changes nothing, and the staging folder plus "refuse if any top-level item exists" means a folder that already exists on a host is never merged into by accident, or half replaced. Merging into or replacing a folder is a decision a person should make with a file manager, not a send. `extract` needs a `.zip` and files_write on every target, like any send.
- **Rejected:** one transfer per file with `mkdir -p` on every host (thousands of rows, the audit log drowned). Overwriting or merging into a folder that exists (silent damage; D-39 refuses the same for copy). Unpacking with a system `unzip` command (a dependency on the host's tools, and the flags that make it safe vary). Sending the zip as it is and leaving the unpacking to the person (that is what the plain send already does). A new session kind to stream a folder to the server (the `download` session already does it).
- **Consequence:** an agent older than 0.6.0 cannot unpack: that transfer fails with an error. Nothing runs from the clone's folder, so it does not matter where the person put it or who may enter it (a clone under `/root` cannot be entered by another user). Go itself downloads the toolchain a project asks for, so the script only needs to bootstrap a recent enough Go, not the exact version. Commands that create the first user run as the service's user from `/`, so the database is owned by the right account and no folder permission gets in the way. The script is run with `sh`, so it does not depend on the executable bit surviving a checkout on Windows.
- **Rejected:** committing built binaries to git (large files, stale ones). A Docker image (a second way to run it, and docker on the VPS). `scp` or `rsync` from the laptop (the original guide). A `curl | sh` installer for the server itself (the agent has one because it must be one command on many machines; the server is installed once and a clone is also the source to read). Running the service from the clone's folder (permissions and an unclear update).
- **Consequence:** the VPS needs git, curl, enough memory to build (about 1 GB) and internet access to fetch Go. A build takes about a minute. The script is Debian and Ubuntu minded for Caddy and Go's download, and refuses other systems with a message saying what to do by hand. The clone stays on the server, which is also where `git pull` happens: protect the account that can read it. A change to `deploy/headnode.service` is applied by running `start.sh` again, not by `git pull` alone.

### D-30 — Versioned schema migrations with `PRAGMA user_version` · accepted · 2026-11-20
- **What:** `schema.sql` is now the frozen baseline. Later changes to a table are entries in `migrations` (`server/migrations.go`), applied in order by `OpenDB` to every database, new or old. SQLite's `user_version` records how many have run, each migration and its version number commit together, and a database newer than the program is refused. The first entry adds `agents.wan_addr`.
- **Why:** D-05 said migrations arrive the first time a schema change would break existing data, and D-24 said the next change to an existing table would need one. The database now holds users, groups and enrolled hosts, so deleting it for a new column is no longer a small thing. `user_version` is built into SQLite, so it needs no table and no dependency.
- **Rejected:** deleting the development database again (it holds real setup work now). Editing the `CREATE TABLE` in `schema.sql` (`IF NOT EXISTS` would silently skip it on existing databases). A migration library (a dependency for a handful of statements).
- **Consequence:** never edit or reorder a migration that has shipped: add a new one. Reading the full current schema means the baseline plus the migrations. Two processes that open a freshly upgraded database at the very same moment (the server and a command-line command) could collide once, and one of them reports an error that goes away on retry.
